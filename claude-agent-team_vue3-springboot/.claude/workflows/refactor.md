# 工作流：技术重构（Refactor）

> architect-agent 权重最高，QA 需要做全量回归。

---

## 触发条件

用户输入包含：重构、迁移、技术债务、代码优化、架构调整 等关键词时，走本流程。

---

## 完整流程

```
重构需求
   │
   ▼
Step 1: pm-agent
   ├── 明确重构范围（哪些模块/文件）
   ├── 明确重构目标（解决什么问题）
   ├── 明确完成标准（如何判断重构成功）
   └── → 调用 architect-agent（最重要的一步）

Step 2: architect-agent（核心，权重最高）
   ├── 现状分析：
   │     ├── 梳理当前架构问题和痛点
   │     └── 识别风险点
   ├── 制定重构方案：
   │     ├── 迁移策略（逐模块 / 全量 / 渐进式）
   │     ├── 模块优先级排序
   │     └── 各模块具体的改造方案
   ├── 完成标准：
   │     ├── 功能等价性标准（接口行为不变）
   │     └── 代码质量指标（如覆盖率 > 80%）
   ├── 回滚方案：出现问题时如何快速回滚
   ├── 风险评估：迁移过程中的潜在风险
   └── 输出：重构方案文档

Step 3: [开发 Agents]（按模块分批执行）
   ├── backend-agent：按重构方案逐模块执行
   ├── frontend-agent（如有前端变动）
   └── dba-agent（如有 Schema 变动）

   注意：
   - 严格按 architect-agent 的方案执行，不自行发挥
   - 每个模块完成后通知 pm-agent，不等待全部完成

Step 4: qa-agent（全量回归，重构必须）
   ├── 执行 P0 + P1 + P2 全量测试用例
   ├── 重点验证：
   │     ├── 功能等价性（接口入参/出参不变）
   │     ├── 边界场景和异常场景
   │     └── 性能指标不退步
   └── 输出：全量回归报告

Step 5: reviewer-agent
   ├── 代码质量审查
   ├── 架构合规性（对照重构方案文档）
   ├── 是否有遗漏未重构的部分
   └── 输出：Review 报告
```

## 重构方案文档模板

```markdown
## 重构方案

**重构范围**：{模块列表}
**重构目标**：{解决什么问题}
**预计周期**：{时间预估}

### 现状分析

**问题清单**：
1. {问题1：描述 + 影响}
2. {问题2：描述 + 影响}

### 迁移策略

**策略选择**：逐模块迁移 / 全量迁移 / 渐进式

**执行顺序**：
1. 第一批：{模块列表}（原因：{无依赖/风险最低}）
2. 第二批：{模块列表}
3. ...

**各模块改造方案**：
- {模块A}：{具体改造说明}
- {模块B}：{具体改造说明}

### 完成标准

- [ ] 所有 P0 + P1 测试用例通过
- [ ] 接口入参/出参行为与重构前完全一致
- [ ] 无新增的 TODO / FIXME 注释
- [ ] 代码测试覆盖率 ≥ {X}%

### 回滚方案

如果重构后出现严重问题：
1. Git revert 重构提交
2. {其他回滚步骤}

### 风险评估

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| {风险1} | 低/中/高 | 低/中/高 | {措施} |
```

---

## 关键约束

```
1. architect-agent 输出的重构方案是【唯一依据】，开发 Agent 不得自行发挥
2. qa-agent 必须做【全量回归】（P0 + P1 + P2），不可简化为定向回归
3. 重构过程中不得引入新功能（混入新需求）
4. 每个模块重构完成后必须能独立运行（不能出现半重构状态）
5. 数据库 Schema 变更仍需通过 Flyway 脚本
```

---

## 与新功能开发的区别

| 对比项 | 新功能开发 | 技术重构 |
|--------|-----------|---------|
| architect-agent 职责 | 设计新方案 | 分析现状 + 制定迁移路径 |
| 开发 Agent 约束 | 实现新功能 | 严格按迁移方案执行 |
| QA 范围 | P0 + P1 | P0 + P1 + P2（全量）|
| 交付标准 | 功能可用 | 功能等价 + 代码质量提升 |
